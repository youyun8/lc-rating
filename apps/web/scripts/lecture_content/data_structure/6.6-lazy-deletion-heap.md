## 這個技術解決什麼問題

`priority_queue` 只能 $O(1)$ 看堆頂、$O(\log n)$ 彈堆頂。**它沒有「刪掉中間某個元素」或「修改某個元素」的介面**——找到那個元素本身就要 $O(n)$。

但很多題偏偏需要：

- **掃描線中，元素會「過期」**：218（天際線問題）——建築的右邊界掃過後，它的高度就該從候選中消失。
- **同一個 id 會被反覆更新，舊值作廢**：2034（股票價格波動）、3092、3391。
- **要刪掉指定位置 / 指定值的元素**：2349（設計數字容器系統）、1172（餐盤堆疊）。
- **堆與另一個結構共同維護同一批資料，另一邊刪了這邊也要刪**：716（最大堆疊，見 4.2）、480（滑動視窗中位數，見 6.7）。

**懶刪除的想法**：*不真的刪，只記下「這個元素已經作廢」；等它浮到堆頂時再丟掉。* 因為**堆頂以外的元素永遠不會被讀到**，作廢的元素躲在裡面完全不影響答案。

**辨識訊號**：需要「動態極值 + 刪除任意元素」，而且**刪除是單向的（作廢後不會復活）**。

## 狀態／資料結構定義

三種實作，適用情境不同。

### (A) 雙堆對消——刪除的是「值」

```cpp
priority_queue<int> pq, del;  // 兩個堆用同一個比較器
void push(int x) {
    pq.push(x);
}
void erase(int x) {
    del.push(x);
}  // 只登記，不真刪
int top() {
    while (!del.empty() && del.top() == pq.top()) {
        del.pop();
        pq.pop();
    }
    return pq.top();
}
```
**前提：`del` 中的每個元素都確實在 `pq` 中**（以多重集合計）。使用者必須保證只刪存在的元素。

### (B) 計數表——刪除的是「值」，但不想再開一個堆

```cpp
priority_queue<int> pq;
unordered_map<int, int> pending;  // 待刪次數
int size = 0;
void erase(int x) {
    ++pending[x];
    --size;
}
int top() {
    while (!pq.empty()) {
        int v = pq.top();
        auto it = pending.find(v);
        if (it == pending.end() || it->second == 0) return v;
        if (--it->second == 0) pending.erase(it);
        pq.pop();
    }
    ...
}
```
**(A) 與 (B) 等價**；(B) 省一個堆但多一個雜湊表，實測差不多。**(A) 的優點是不需要 `unordered_map`，在值域大、雜湊碰撞嚴重時更穩。**

### (C) 版本戳記——刪除的是「某個 id 的舊快照」

```cpp
priority_queue<pair<int, int>> pq;  // (value, id)
unordered_map<int, int> cur;        // id -> 目前的權威值
void update(int id, int v) {
    cur[id] = v;
    pq.push({v, id});
}
pair<int, int> top() {
    while (!pq.empty() && cur[pq.top().second] != pq.top().first) pq.pop();
    return pq.top();
}
```
**這是 2034、3092 這類「同一 id 反覆更新」題的標準寫法。** 判斷過期不靠登記，而是**跟一張權威表比對**——這比 (A)/(B) 更省事，因為不需要知道「舊值是多少」。

**(C) 的一個微妙點**：若某 id 的值改成 $v_1$、再改回 $v_0$，堆中早先那個 $(v_0, id)$ 的舊條目會被判定為「有效」。**這不是 bug**——它的值確實等於當前權威值，用它回答完全正確。**「按值比對」在值回到原狀時會意外復活，但復活的那份與現況一致，所以無害。** 若條目還帶有其他欄位（例如時間戳），就必須改用真正的版本號而非值。

## 不變量或正確性證明

### 定理 1（雙堆對消的正確性）

*不變量 (D)*：任一時刻，**真實集合（多重集合）$= \mathrm{ms}(\texttt{pq}) - \mathrm{ms}(\texttt{del})$**，且 $\mathrm{ms}(\texttt{del}) \subseteq \mathrm{ms}(\texttt{pq})$。

*定理*：`top()` 的清理迴圈結束後，`pq.top()` 就是真實集合的最大值。

*證明*。兩個堆使用**同一個比較器**，故 `pq.top()` 是 `pq` 的最大值、`del.top()` 是 `del` 的最大值。
- 若 `del.top() == pq.top()`：這個最大值有一份已被登記刪除，兩邊同時彈出，(D) 保持（兩邊各減一份相同元素）。
- 若 `del.top() != pq.top()`：由 $\mathrm{ms}(\texttt{del}) \subseteq \mathrm{ms}(\texttt{pq})$ 得 `del.top() <= pq.top()`；不相等即 `del.top() < pq.top()`。於是 `pq.top()` 這個值在 `del` 中一份也沒有（`del` 的最大值都比它小），故它屬於真實集合，且是其中最大者（真實集合 $\subseteq$ `pq`）。$\square$

**「兩個堆必須用同一個比較器」是最常被忽略的前提。** 一邊 `less` 一邊 `greater`，這段程式碼會安靜地給出錯誤答案。

### 定理 2（攤還複雜度）

**每個元素最多被推入 `pq` 一次、被彈出一次；`del` 同理。** 故 $q$ 次操作（含 $d$ 次刪除）的堆操作總數 $\le 2(q + d)$，總時間 $O((q+d)\log(q+d))$。

*位能論證*：令 $\Phi = |\texttt{pq}| + |\texttt{del}|$。清理迴圈每執行一輪，$\Phi$ 減 2，而每次 `push`／`erase` 只讓 $\Phi$ 增 1。**故清理迴圈的總執行次數不超過總推入次數**——`while` 迴圈同樣不會讓複雜度退化。$\square$

**這與 4.7、5.4、6.5 的攤還論證是同一條。** 看到 `while (…) pop()` 就以為是 $O(n)$ 單次，是反覆出現的誤判。

### 定理 3（懶刪除的適用前提：單向失效）

懶刪除成立需要：**一個元素一旦被判定作廢，就永遠作廢。**

*理由*：清理迴圈把作廢元素**物理刪除**了。若它之後又該變回有效，資料已經沒了。

*檢查表*：
- (A)(B)：登記刪除後不會撤銷 ✔（`erase` 沒有逆操作）。
- (C)：判定依據是「$\ne$ 當前權威值」。**這不是單向的**（值可能改回來），但如前所述，改回來時舊條目與現況一致，仍然正確。**真正危險的是「條目攜帶額外資訊」的情形**——例如 (value, id, timestamp)，值改回來但時間戳不同，用舊條目就錯了。此時必須用嚴格遞增的版本號比對。
- **4.2 的 1172（餐盤堆疊）** 是弱不變量的例子：堆是「非滿堆疊下標」的**超集合**，讀取時要驗證 `stacks[i].size() < capacity`。單向性由「一個堆疊被填滿後只可能因 `pop` 而變回非滿，而 `pop` 會重新推入」保證。**這裡的單向性不是自動成立的，是靠 `pop` 主動補推入來維持的**，讀 1172 的程式碼時要看清楚這一點。

### 定理 4（218 天際線：事件排序的三條規則就是幾何語意）

把每棟建築 $(l, r, h)$ 拆成兩個事件：$(l, -h)$「進場」與 $(r, +h)$「離場」。所有事件按 `pair` 的字典序升冪排序。

**這個 $\pm h$ 的編碼一次解決三個並列情形，每一條都對應一個幾何事實：**

1. **同一 $x$ 上，進場排在離場之前**（因為 $-h < 0 < +h$）。
   *理由*：兩棟建築在同一點相接時，天際線不應該掉到地面再升起來。
2. **同一 $x$ 上的多個進場，高的排前面**（$-h$ 小者在前 ⇔ $h$ 大者在前）。
   *理由*：高的先進場，較矮者進場時不會產生新的關鍵點，避免輸出重複點。
3. **同一 $x$ 上的多個離場，矮的排前面**（$+h$ 小者在前）。
   *理由*：矮的先離場不改變當前最大高度；高的最後離場，只產生一個關鍵點。

*演算法*：大頂堆存「目前在場的高度」，離場事件用懶刪除登記。每處理完一個 $x$ 上的所有事件後，取清理後的堆頂 $H$（空則 0）；**若 $H \ne$ 上一次記錄的高度，就輸出 $(x, H)$。**

*不變量*：處理完 $x$ 上的所有事件後，堆（清理後）恰為「所有 $l \le x < r$ 的建築高度」的多重集合，故堆頂即該點的天際線高度。

*為什麼「$H \ne$ 前一次」這個判斷就足以去除多餘點*：關鍵點的定義是「高度發生變化的位置」。因為我們在**每個 $x$ 的所有事件處理完之後**才讀取一次高度，中間的臨時狀態不會外洩。$\square$

**218 是「掃描線 + 懶刪除堆」的教科書題**，值得完整寫一遍。另解是用 `multiset<int>`（`erase(find(h))` 精確刪除）——程式碼更短，但常數更大。

### 定理 5（什麼時候不該用懶刪除）

**空間**是懶刪除唯一的真實代價：**作廢的條目在浮到堆頂之前都不會被回收。**

- *最壞情形*：某個 id 被更新 $m$ 次但從未成為堆頂，堆中就躺著 $m-1$ 個垃圾。$q$ 次操作最壞 $O(q)$ 空間，**即使真實集合只有 1 個元素。**
- *緩解*：記錄垃圾數 `garbage`，當 `garbage > pq.size() / 2` 時**整堆重建**（把有效元素倒出來 `make_heap`）。重建 $O(n)$，且兩次重建之間至少產生 $n/2$ 個垃圾，**攤還 $O(1)$**。
- *替代方案*：`std::multiset`／`std::map` 支援 $O(\log n)$ 精確刪除，**空間恆等於真實大小**。2034（股票價格波動）與 2349（設計數字容器系統）用 `multiset`／`map<int, set<int>>` 都比懶刪除堆短且無垃圾問題。

**判準**：
| 情境 | 推薦 |
| --- | --- |
| 刪除次數遠少於插入，或元素本來就會很快浮上堆頂（掃描線） | 懶刪除堆 |
| 刪除頻繁、記憶體吃緊、或需要 `lower_bound` | `multiset` / `map` |
| 需要 decrease-key（Dijkstra 稠密圖） | 索引堆，或直接懶刪除（重複入堆） |

**Dijkstra 的標準寫法其實就是懶刪除**：不做 decrease-key，而是重複推入 $(dist, v)$，彈出時檢查 `d > dist[v]` 就跳過。**「重複入堆 + 出堆時驗證」是懶刪除最常見的化身，只是大家不這麼叫它。**

## 時間與空間複雜度

| 操作 | 懶刪除堆 | `multiset` |
| --- | --- | --- |
| `push` | $O(\log n)$ | $O(\log n)$ |
| `erase(x)` | $O(\log n)$（只登記） | $O(\log n)$（`erase(find(x))`） |
| `top` | 攤還 $O(\log n)$ | $O(1)$（`*rbegin()`） |
| 空間 | $O(\text{總操作數})$ 最壞 | $O(\text{真實大小})$ |
| 常數 | 小（連續記憶體） | 大 3–5 倍（紅黑樹節點） |

| 題目 | 時間 | 空間 |
| --- | --- | --- |
| 218 天際線問題 | $O(n\log n)$ | $O(n)$ |
| 2034 股票價格波動 | 每次操作 $O(\log n)$ | $O(n)$（懶刪除最壞） |
| 2349 數字容器系統 | 每次操作 $O(\log n)$ | $O(n)$ |
| 1172 餐盤堆疊 | 攤還 $O(\log n)$ | $O(n)$ |
| Dijkstra（懶刪除版） | $O(E\log E)$ | $O(E)$ |

**注意 Dijkstra 是 $O(E\log E)$ 而非 $O(E\log V)$**——因為堆中最多有 $E$ 個條目（每條邊可能推入一次）。**兩者只差常數（$\log E \le 2\log V$），但答題時說清楚更精準。**

**`erase(find(x))` vs `erase(x)`**：`multiset::erase(x)` 會刪掉**所有**等於 $x$ 的元素，`erase(find(x))` 只刪一個。**這是 `multiset` 用於懶刪除替代方案時最常見的錯誤**（2.7 已提過同一件事，值得再記一次）。

## 與相似技巧的比較

- **與 6.1 基礎堆**：懶刪除只是在基礎堆外面加一層「有效性驗證」。**核心洞見是「堆頂以外的元素從不被讀取，所以垃圾躲在裡面無害」。**
- **與 `multiset`**：功能上 `multiset` 全面覆蓋懶刪除堆，還多了 `lower_bound`。**懶刪除的唯一優勢是常數與快取局部性**；在 $10^5 \sim 10^6$ 量級且時限緊時，這個優勢是實質的。
- **與 5.4 單調佇列**：單調佇列的「頭端過期」也是一種刪除，但它**不需要懶刪除**——因為過期元素恆為前綴，可以直接彈。**「被刪的恆為某一端的前綴」⇒ 用佇列；「被刪的位置任意」⇒ 懶刪除或 `multiset`。**
- **與 4.2 的 1172 / 716**：4.2 從「堆疊設計」的角度看同一個技巧。**716 的 `popMax` 之所以要放棄輔助堆疊改用 `list + map`，正是因為堆疊的懶刪除會破壞 LIFO 順序**——懶刪除只對「無序容器 + 只讀極值」安全。
- **與 6.7 對頂堆**：480（滑動視窗中位數）必須在兩個堆上同時做懶刪除，**額外的難點是「兩邊的有效大小」不再等於 `heap.size()`**，必須另外用計數器追蹤。見 6.7。
- **與並查集（8.x）**：若「刪除」的語意是「這個位置用掉了，下次找下一個可用的」，並查集的「指向下一個可用位置」寫法是 $O(\alpha)$，比任何堆都快。**判準：刪除後要找的是「相鄰的下一個」而非「全域極值」。**
- **與離線處理（12.x）**：若所有刪除時機事先已知，可以離線排序後用掃描線一次處理，完全避開刪除。**能離線就離線，這通常是最快的路。**

## 本節重點速查

- **核心洞見：堆頂以外的元素從不被讀取，所以作廢的元素躲在堆裡無害——等它浮上來再丟。**
- 三種寫法：**(A) 雙堆對消**（刪值）、**(B) 計數表**（刪值）、**(C) 版本戳記**（刪某 id 的舊快照，跟權威表比對）。**同一 id 反覆更新就用 (C)。**
- **(A) 的兩個前提**：兩個堆用**同一個比較器**、`del` 是 `pq` 的子多重集合。前者寫錯會安靜地給錯答案。
- **適用前提是「單向失效」**（定理 3）：作廢後不復活。(C) 按值比對時值可能改回來，但那份與現況一致，無害；**若條目攜帶額外欄位就必須用真正的版本號。**
- **攤還 $O(\log n)$**：每個條目最多入堆出堆各一次；`while` 清理迴圈不會退化。
- **唯一的代價是空間**：垃圾最壞 $O(\text{操作數})$。緩解是「垃圾過半就整堆重建」（攤還 $O(1)$）。
- **218 的事件編碼 $(l, -h)$／$(r, +h)$ 一次解決三種並列**：進場先於離場、進場高者先、離場矮者先——每條都對應一個幾何事實。**每個 $x$ 的事件全部處理完才讀一次高度，才能正確去重。**
- **Dijkstra 的「重複入堆 + 出堆驗證」就是懶刪除**，複雜度 $O(E\log E)$。
- `multiset::erase(x)` 刪全部，`erase(find(x))` 只刪一個。
- **判準**：刪除的是「某端的前綴」⇒ 佇列；「全域極值 + 任意刪除且刪除不多」⇒ 懶刪除堆；「刪除頻繁或要 `lower_bound`」⇒ `multiset`；「刪除時機全部已知」⇒ 離線掃描。
