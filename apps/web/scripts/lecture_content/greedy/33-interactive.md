## 這個技術解決什麼問題

看不到完整輸入，資料藏在系統手裡，只能透過詢問函式一次問一點，再依回答決定下一步。目標通常是在限定的詢問次數內定位答案。

## 狀態／資料結構定義

維護一個「仍可能是答案的候選集合」，通常表示成一個區間 `[lo, hi]` 或一組尚未排除的候選。每次詢問都應該顯著縮小它。

## 不變量或正確性證明

不變量：答案始終落在當前的候選集合內。

這是互動題唯一需要嚴格維持的性質。每次詢問後，必須確認「被排除的候選確實不可能是答案」，否則不變量被破壞，後續全錯。

詢問次數的下界由**資訊論**給出：若候選有 `N` 種可能，而每次詢問最多有 `k` 種不同回答，則詢問次數至少為 $\lceil \log_k N \rceil$——因為 `t` 次詢問最多區分 $k^t$ 種情形，必須不小於 `N`。

由此可知二元回答（是／否、大／小）的最優策略是每次把候選對半分，這正是二分搜尋；若題目允許三種回答，則每次分成三份，次數降為 $\log_3 N$。設計策略時應先算出這個下界，再確認自己的方法是否達到——若差距很大，通常代表詢問方式沒有充分利用回答的資訊量。

例如「猜數字 1 到 n，每次回答偏大或偏小或正確」的下界是 $\log_2 n$，二分即達到；若改成「只回答是否整除」，每次的資訊量就不同，策略也要跟著改。

## 逐步演算法

確認每次詢問能得到幾種回答；算出次數下界；設計能均勻切分候選集合的詢問；每次詢問後更新候選並確認不變量；候選只剩一個時輸出。

## C++17 模板

```cpp
// 猜數字：guess(x) 回傳 -1（偏大）、1（偏小）、0（猜中）。
int guessNumber(int n) {
    int lo = 1, hi = n;
    while (lo <= hi) {
        const int mid = lo + (hi - lo) / 2;  // 避免相加溢位
        const int result = guess(mid);
        if (result == 0) {
            return mid;
        }
        if (result < 0) {
            hi = mid - 1;
        }  // 偏大，答案在左半
        else {
            lo = mid + 1;
        }
    }
    return -1;
}
```

## 常見錯誤與邊界條件

- 詢問回傳值的方向理解反了（是「我猜的太大」還是「答案太大」）。
- 中點計算溢位。
- 忘記在互動題中刷新輸出緩衝（某些評測系統需要 `fflush` 或 `endl`）。
- 詢問次數超過上限。
- 候選集合更新時漏掉邊界值而排除掉正確答案。

## 與相似技巧的比較

互動題的骨架多半是二分或分治，差別在於「比較的對象要透過詢問取得」而非直接讀取；若每次詢問成本不同，則變成最優決策樹問題，需 DP 求解。設計時先算資訊論下界，能快速判斷方向是否正確。

## 本節重點速查

- 維持「答案仍在候選內」的不變量
- 用 $\log_k N$ 估下界
- 每次詢問要盡量均分候選
- 注意輸出緩衝與詢問上限。

## 時間與空間複雜度

詢問次數為 $O(\log_k N)$，每次詢問的本地計算為 $O(1)$，空間 $O(1)$。
