## 這個技術解決什麼問題

主動在演算法中加入隨機，用「猜一個候選再快速驗證」換取簡短又高效的解法。適用於答案在資料中佔比夠高、且驗證成本低的場合。

## 狀態／資料結構定義

通常只需一個隨機引擎與一個驗證函式。迴圈重複若干輪，每輪隨機抽一個候選並以 $O(n)$ 驗證，命中即回傳。

## 不變量或正確性證明

設答案在資料中佔比至少為 `p`（例如「出現次數超過一半的元素」對應 $p > 1/2$）。單輪抽中的機率至少為 `p`，故連續 `k` 輪都失敗的機率不超過 $(1-p)^k$。

以 $p = 1/2$、$k = 30$ 為例，失敗機率不超過 $2^{-30} \approx 10^{-9}$，遠低於一般題目可接受的誤差。這說明輪數只需常數次即可把錯誤率壓到可忽略——關鍵在於失敗機率呈**指數**下降。

正確性的另一半來自驗證：抽中候選後必須確認它真的是答案。因為驗證是確定性的，演算法永遠不會輸出錯誤答案，只可能在極小機率下沒找到答案（屬於 Las Vegas 型；若改為固定輪數後直接回傳最佳候選，則成為 Monte Carlo 型，需接受微小錯誤率）。

隨機化還能防止「被卡」：對手無法針對我們的隨機源構造最壞輸入，因此期望複雜度不依賴輸入分布。這也是雜湊題中加隨機種子以避開反雜湊資料的理由。

## 時間與空間複雜度

`k` 輪、每輪驗證 $O(n)$，總計 $O(kn)$；`k` 為常數時即 $O(n)$。空間 $O(1)$。

## C++17 模板

```cpp
// 隨機化找出現次數超過一半的元素（配合 O(n) 驗證）。
int majorityElement(const vector<int>& nums) {
    mt19937 rng(chrono::steady_clock::now().time_since_epoch().count());
    uniform_int_distribution<int> pick(0, nums.size() - 1);
    const int need = nums.size() / 2;

    for (int round = 0; round < 30; ++round) {  // 失敗機率約 2^-30
        const int candidate = nums[pick(rng)];
        const int count = std::count(nums.begin(), nums.end(), candidate);
        if (count > need) {
            return candidate;
        }
    }
    return -1;  // 實務上不會走到
}
```

## 常見錯誤與邊界條件

- 種子固定（例如 `mt19937 rng(0)`）而被構造資料卡住。
- 輪數過少使失敗機率不可忽略。
- 跳過驗證直接回傳候選。
- `rand() % n` 的模偏差。
- 答案佔比其實不高卻硬套（此時期望輪數會爆炸）。

## 與相似技巧的比較

摩爾投票法能確定性地在 $O(n)$ 時間、$O(1)$ 空間解出多數元素，比隨機化更可靠，應優先採用；隨機化的價值在於那些確定性解法很複雜、而驗證卻很簡單的題目。雜湊、字串指紋、Miller-Rabin 都屬同一族思路。

## 本節重點速查

- 猜加驗證
- 失敗機率指數下降，常數輪就夠
- 務必用時間或 `random_device` 當種子
- 有確定性解法時優先用它。
